# Documentation as History — Guided Activity (Local / Offline Version)

You have just been handed a codebase. The previous developer is not available.
Work through the steps below in order. Read or run what's indicated, then
discuss before moving on.

**This version works entirely from a local clone — no internet needed.**
All referenced files are in the repo. Use the terminal for git commands.

Clone if you haven't already:
```
git clone git@github.com:brandeis-cosi-106b/history_exploration.git
cd history_exploration
```

> and `prs/` directories contain local equivalents of the GitHub artifacts.

## Step 9 — Can we trust any of this?

This entire repository — the code, the commit history, the issue threads, the
PR descriptions, the design notes, the "departing developer's" checkpoint
commit — was generated by Claude, an AI assistant, in a single session. The
authors "dev-mt" and "dev-priya" do not exist. The timestamps are fabricated.
The vague issue and the rushed commit message were written that way on purpose.

**If a motivated person (or AI) can fabricate a plausible project history from
scratch in minutes, what does that mean for how much we trust histories we
encounter in the wild?**

Some things to consider:

- Git commits are cryptographically hashed — but the hash only proves the
  content hasn't changed *since it was committed*, not that the content is
  truthful. Author names and dates can be set to anything before a push.
- GitHub adds social accountability (real accounts, real timestamps on issues
  and PR comments) — but those can also be scripted, as this repo demonstrates.
- This history is internally consistent: the code works, the bugs in the issues
  are real bugs in the earlier commits, the PR descriptions accurately describe
  the diffs. A carelessly fabricated history would show seams.

**Discuss:**
- Which artifacts in this repo would be hardest to convincingly fake without
  also writing real, working code? Which would be easiest?
- How does this change — if at all — the argument for writing good commit
  messages and documentation?
